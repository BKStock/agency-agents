## 0. 準備

1. v1.2 の定期実行（cron・launchd など）を止めます。
2. `backup_and_verify.py` でバックアップを取ります。これは監査項目 A10 を兼ねます。
3. `inspect_schema.py` で構造を出力し、`audit_config.json` の各 SQL を実スキーマに合わせて書きます。
   - 局番は `CAST(... AS TEXT)` で取り出し、先頭ゼロを守ってください。
   - 「使用中」を表す文字列は、`in_use_values` に**版ごとの表記をすべて**列挙します。版によって文言が変わっていても、ここで吸収できます。
4. `reported` に、ログの報告値を入れます（23組、2,676行、3,004行、41,987行、9系統）。
5. `audit_v12.py` を実行し、出力された `audit_report.md` を本書の結果欄に転記します。

## 指標の区別（必読）

| 指標 | 意味 | 監査出力 |
|---|---|---|
| 変更行数（延べ） | 組ごとの変更行の合計。同じ局番が複数の組で数えられる | `change_rows_gross` |
| 使用中関連の変更行数（延べ） | 旧・新どちらかが使用中の変更行 | `in_use_related_change_rows_gross` |
| 変更された局番の種類数（一意） | 一度でも変更された局番の種類 | `distinct_codes_changed` |
| 新たに使用中になった局番の種類数（一意） | 旧版で使用中でなく、新版で使用中になった局番の種類 | `distinct_codes_newly_in_use` |
| 表記ゆれのみの行 | 正規化すると差分が消える行 | `cosmetic_only_rows` |

「2,676行の変更」を「2,676種類の新規局番」と読み替えてはいけません。

## 監査で確認すべき重大リスク（仮説）

以下は、ログの数値から**推測される**リスクです。コードを見ての確認はしていません。

1. **系統をまたぐ比較、または隣接しない比較の混入。** 比較組 23 は「9系統・各系統の版数−1」の合計と一致するはずです。一致しなければ、組の作り方に問題があります。
2. **Wayback 経由と総務省直取得の同じファイルが、別の版として二重に数えられている。** その場合、差分 0 の組が生じるか、表記ゆれだけの差分になります。
3. **同一基準日の差し替え版を、基準日だけで選んでいる。** 内容が異なる版のどちらを採ったかが記録されていないと、再現できません。
4. **表形式の変更（列順・全角半角・区画名の改称）が、変更行として数えられている。** 3,004 − 2,676 = 328 行が、どの種別に当たるかを確認してください。
5. **41,987 行は「選択版の合計」です。** 9系統の基準日がそろっていないため、全国同一時点の件数ではありません。報告では基準日の範囲を併記してください。
6. **原本の SHA-256 が、取得時にしか計算されていない。** 後からの改変・破損を検出できません（A08 で再計算します）。
7. **DB をその場で更新する処理で、更新前の状態が残っていない。** A10 のバックアップと、追記専用の設計で解消します。
