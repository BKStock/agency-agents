## 2. 分類定義の改善提案

詳細は [01_class_definitions.md](01_class_definitions.md) にあります。

1. **R軸と L軸を独立に評価します。** 地方都市の戸建地は R2 と L4 の両方に該当してよく、軸ごとに主分類を持ちます。1地域に1分類しか許さない設計にはしません。
2. **L6 は属性クラスにします。** 主分類にはせず、L1〜L3 のいずれか、または DID 外という「集落性の文脈」があるときだけ有効にします。文脈が資料不足なら保留にします。
3. **R1 の地価は都道府県内の相対値で比べます。** 全国の絶対額で比べると、地方の高級住宅地を拾えないためです。
4. **R3/R4 は外部証拠がなければ確定にしません。** 町丁目の「建て方」と「所有関係」は別々の周辺集計で、共同住宅率と持ち家率がどちらも高くても、持ち家が戸建側に偏っている可能性を排除できません。この制約は、ルールファイルの読込時に強制します（外せません）。
5. **R5 は公営・UR の台帳で確定します。** 民間の分譲団地は国勢調査では区別できません。
6. **L2 は境界データの入手可否で運用を分けます。** 漁業集落のポリゴンが公的に入手できない場合は、漁港距離などの代替指標を使い、候補（candidate）止まりにします。
7. **L4 の「地方都市」を、三大都市圏外かつ都市雇用圏内と定義します。** 曖昧さをなくすためです。
8. **L5 は国勢調査では確定できないことを、制度上の制約にします。** 二次的住宅（住宅・土地統計調査）は市区町村単位の事前情報としてだけ使います。
9. **非住宅地域を、新しい分類として増やしません。** 工業地や業務地区は「該当分類なし」（軸の状態 `none`）で表します。無居住地は `undeterminable` で表します。

## 3. L1〜L6 判定エンジンの詳細設計（R分類と共通）

### 3.1 データの流れ

```
e-Stat 小地域集計 ─┐
e-Stat 境界        ├─ normalize ─▶ town_master / town_feature（load_id 付きで追記）
経済センサス       ┘                     ▲
GIS（農業集落・L03-b・A29・DEM）── gis.py ─┘
外部証拠（PLATEAU・台帳）────────────▶ external_evidence
                                          │
rules_vX.json ─▶ rules.parse_rules（不変条件を検証）
                                          ▼
                  engine.classify ─▶ classification_run（ルール本文・入力ハッシュ・最大 load_id）
                                   ├▶ regional_classification（町丁目×12分類、全行）
                                   └▶ town_axis_result（R軸・L軸の主分類）
```

### 3.2 1分類の判定手順（`engine._evaluate_class`）

1. 条件の特徴量が1つでも `missing` / `suppressed` なら、`insufficient_data` とします。理由欄に不足した特徴量を記録します。
2. `undefined`（分母が 0）なら、`undeterminable` とします。
3. すべての条件を満たさない場合は、外れた条件がすべて閾値近傍（許容幅 3%）かどうかで分けます。
   - 近傍なら `on_hold`
   - そうでなければ `not_applicable`
4. 条件を満たした場合は、排他条件を確認します。
   - R2 の場合、R1 に該当すれば `not_applicable` とします。
   - R1 が保留・資料不足なら、R2 は候補止まりです。
5. 文脈条件を確認します（L6）。
   - L1〜L3 のいずれかに該当、または DID 外なら有効です。
   - 文脈が判定できなければ `on_hold`、文脈がなければ `not_applicable` とします。
6. 必要な外部証拠（等級 A/B）とルールの承認状態を確認します。
   - どちらかが欠ければ `candidate`
   - どちらもそろえば `confirmed`

### 3.3 L分類それぞれの判定内容

| 分類 | 主な特徴量 | 計算方法 |
|---|---|---|
| L1 | 農業集落の重複率、農地比率、DID、一般世帯 | `gis.overlap_ratio`（農業集落境界）、`gis.category_area_ratios`（L03-b の田・その他農用地） |
| L2 | 漁業集落（または代替）の重複率、DID、一般世帯 | 漁業集落ポリゴン、または漁港からのバッファを `overlap_ratio` で計算 |
| L3 | 森林比率、平均傾斜、DID、一般世帯 | L03-b の森林、`gis.dem_stats`（10m DEM） |
| L4 | 三大都市圏外、都市雇用圏、住居系用途地域比、人口密度 | 市区町村の属性を町丁目に付与、A29、国勢調査 |
| L5 | 二次的住宅比率（市区町村）＋外部証拠 | 住宅・土地統計調査＋台帳・PLATEAU |
| L6 | 高齢化率、10年人口増減率＋集落性の文脈 | 2010年人口を 2020 年境界へ組み替えて計算（[02](02_data_sources.md) §2） |

### 3.4 主分類・副分類・重複

`primary.assign` が担います。

- 並べ方は (確定度, 根拠等級, 根拠スコア) です。優先順位の固定表は持ちません。
- 拮抗した場合は `on_hold` とします。
- L6 は主分類になりません。
- 町丁目全体で該当分類が2つ以上あれば、`overlap_flag` を付けます。

### 3.5 再分類と履歴

- 新しい統計や GIS を取り込むと、新しい `load_id` が付きます。この状態で `classify` を実行すると、新しい run になります。
- 過去の run は消えません。トリガーで UPDATE / DELETE を拒否しています。
- `reproduce(run_id)` は、保存したルール本文と最大 `load_id` で再計算し、全行を照合します（受入 12）。
- 最新の結果は `current_classification` ビューで参照します。

### 3.6 発見エンジン（P3、設計）

目的は、**番号指定データに載っている局番**について、調査する優先順位を付けることです。番号を生成・探索するのではありません。対象は次の2種類です。

- 番号区画内のどの町丁目でも、公開施設での観測がまだない局番
- 新しく指定された局番

優先度は、次の要素を組み合わせて決めます。

- 指定の新しさ（新規指定日）
- 番号区画の市区町村構成（whole / part）
- 同じ区画内の観測済み局番の分布
- 12分類の構成

出力は「調査候補の局番 × 確認すべき公開施設の種別 × 町丁目の候補」です。各候補には、根拠と信頼性（観測・区画・推定の別）を付けます。

### 3.7 規模と性能

- 2020年の小地域は全国で約 20 万地域規模になる見込みです（正確な数は取込時に確認）。12分類を掛けると約 250 万行です。SQLite で十分扱えます。
- GIS の重複計算は、都道府県ごとに分けてバッチ処理します。集落境界は都道府県ごとに union してから交差を取ります。

### 5.2 データの完全性を守る仕組み

- **先頭ゼロの保持**：行政コードは TEXT です。都道府県と市区町村の整合は CHECK 制約で検証します。float 値は取込時に拒否します（Excel で数値として読まれたコードを防ぐため）。
- **欠損とゼロの区別**：`state` の CHECK 制約で強制します。`observed` / `zero` 以外の状態では、値は NULL でなければなりません。
- **合算の整合**：`secrecy_state='merged_into_other'` のときは、合算先 `merged_into` が必須です。
- **主分類の制約**：`primary_flag` と `secondary_flag` は同時に立てられません。主分類は `confirmed` / `candidate` に限ります。

## 6. GIS・統計解析の実装方法

1. **座標系**：保存は JGD2011（EPSG:6668）です。面積は GRS80 楕円体上の測地線面積（`pyproj.Geod`）で計算します。こうすると平面直角座標系の系番号に依存せず、系をまたぐ北海道・東京島しょ・沖縄・鹿児島も一律に扱えます（`test_gis.test_reprojected_input_gives_same_ratio`）。
2. **取得範囲**：重複率を計算する前に、対象レイヤの取得範囲（coverage）に町丁目が含まれるかを確認します。範囲外は 0 ではなく `missing` とします。
3. **海域・無居住地**：面積 0 は `undefined` とし、分類は `undeterminable` とします。一般世帯 0 の町丁目は、L1〜L3 の「一般世帯 ≥ 1」の条件で非該当になります。
4. **DEM**：基盤地図情報の GML を GeoTIFF に変換してから使います。地理座標系の DEM では、緯度に応じて画素の大きさをメートルに換算し、傾斜を計算します（合成 DEM で約 12.2° を検証済み）。
5. **土地利用比率**：L03-b のメッシュ（区分コード）を町丁目と交差させ、区分ごとの面積比を求めます。区分コードと特徴量の対応表は、年版の定義書に合わせて設定ファイルに持ちます。
6. **地価のパーセンタイル**：町丁目内の地価公示・地価調査の地点の中央値を求め、都道府県内で順位を付けて 0〜1 に変換します。地点がない町丁目は missing です（近傍補間は P1 で検討し、使う場合は `proposed` として区別）。
7. **人口の組替え**：[02_data_sources.md](02_data_sources.md) §2 のとおりです。組み替えられない地域は missing とし、L6 は `insufficient_data` になります。
8. **品質指標**：都道府県別に、特徴量ごとの observed / missing / suppressed の件数を `08_classification_quality.csv` とダッシュボードに出します。

## 7. 12分類の検索・出力画面設計

### 7.1 検索条件（実装済み：`query.SearchFilter` / CLI `search`）

指示書 §8 の全条件で絞り込めます。

- 地域：都道府県、市区町村、町丁目（キーの前方一致、または名称の部分一致）
- 分類：R1〜R6・L1〜L6（複数指定可）、複数分類の同時該当（`--require-all`）、軸、主分類のみ

検索結果の各行には、`source_url`（統計の出典）と `phone_relations`（指定原本・観測元の URL）が付きます。観測がない場合は `no_observation`（利用されていないという意味ではない）と明示します。

## 8. 既存 v1.2 の重大な技術的問題（監査で確認すべき仮説）

詳細と検査方法は [03_v12_audit_procedure.md](03_v12_audit_procedure.md) にあります。

1. **変更行数と新規局番数の混同。** 2,676 / 3,004 は延べの変更行数です。新たに使用中になった局番の種類数とは別の指標です（A02〜A04）。
2. **比較組の正当性。** 23組が「系統内で隣接する版」だけでできているかを確認します。系統をまたぐ比較や、隣接しない比較が混じっていないかが論点です（A01）。
3. **同一原本の二重計上。** Wayback 経由と直接取得で、同じファイルが別の版として数えられていないかを確認します（A06）。
4. **同一基準日の差し替え版。** どちらを選んだかが記録されていないと、結果を再現できません（A09）。
5. **表形式変更による見かけの差分。** 全角半角・列順・区画名の改称によるものです（A05）。
6. **先頭ゼロの欠落。** xlrd は数値セルを float で返すため、市外局番「06」が 6.0 になる恐れがあります。v1.2 の取込処理で、コードを文字列として扱っているかをコードで確認してください（監査 SQL でも `CAST(... AS TEXT)` の結果を目視）。
7. **原本の SHA-256 を再検証していない可能性**（A08）。
8. **DB のその場更新で、過去の状態を復元できない可能性**（A10。本設計は追記専用にしました）。
9. **41,987 行を全国件数と誤読する恐れ。** 系統ごとに基準日が異なることを、出力に併記してください。
10. **単一スクリプト（`national_phone.py`）に機能が集中している。** 分類エンジンを同居させると、番号側の変更が分類結果に波及します。本設計では別モジュール・別 DB に分けました。
